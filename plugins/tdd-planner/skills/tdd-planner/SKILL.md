# TDD 계획 — 계약을 쓰는 시간

사이클이 계약의 이행이라면, 계획 단계는 **계약을 쓰는 시간**이다. 코드 수정이 차단된 계획 모드에서 컨텍스트를 쌓고, 합의 산출물(spec·testlist·refactorlist)을 남긴 뒤 사이클 실행에 인계한다.

**계획 모드에 진입해 시작한다.** 진행 중이던 작업을 **재개**하는 세션은 이 스킬이 아니다 — spec·리스트 파일이 복원 지점이며, 사이클 실행 쪽(`ai-tdd` 스킬이 있으면 그것)으로 바로 간다.

## 1. 도메인 탐구 — 질문으로 규칙을 끌어낸다

**규칙은 받아쓰는 게 아니라 질문으로 끌어낸다.** 사용자가 규칙 문서를 주는 경우도 있지만, 대개는 "이런 걸 만들고 싶다" 수준에서 시작한다. 어느 쪽이든 AI가 물어서 좁히는 편이 빠르고 정확하다 — 사용자는 머릿속 규칙을 빠짐없이 나열하지 못하고, AI는 빈칸을 추측으로 채우면 오라클을 오염시킨다.

진입 경로에 따라 무게가 다르다:

- **규칙 문서·상세 설명이 있으면** — 먼저 읽고, **확인·충돌 질문만** 한다 (모순, 예시와 규칙의 불일치, 문서가 침묵하는 입력)
- **주제만 있으면** — 아래 탐구 절차로 규칙을 함께 만들어간다
- **기존 시스템 위의 작업이면** — 사용자만이 정보원이 아니다. 관련 코드·테스트·이슈/PR 이력을 먼저 훑어 **현재 동작**을 파악하고 "지금은 이렇게 동작합니다"로 확인받는다. 단 **코드는 현재를 말할 뿐 당위를 말하지 않는다** — 버그이거나 이미 폐기된 정책일 수 있으므로, 유지할 행동인지 반드시 사람에게 묻는다

### 묻는 법

- **한 번에 2~4개씩 묶어 묻는다.** 한 문항씩 왕복하면 지친다. `AskUserQuestion`처럼 선택지를 제시할 수 있으면 활용한다
- **추상적으로 묻지 말고 구체 시나리오를 들이댄다.** "할인 규칙이 어떻게 되나요?"(❌) → "5만원 주문에 쿠폰 2장이면 얼마인가요? 중복 적용이 되나요?"(⭕). 사용자는 규칙보다 사례에 더 정확히 답한다
- **항상 선택지 + 추천을 붙인다.** "A안(추천, 이유), B안(트레이드오프)" 형태면 사용자는 고르기만 하면 된다. 추천 없는 열린 질문은 초반 한두 개까지만
- **모르는 것은 지어내지 않는다.** 도메인 사실(요율, 임계값, 업무 관행)을 AI가 채우면 그 오류가 오라클→테스트→구현으로 전파된다. 불확실하면 묻거나, 가정임을 명시하고 사용자 확인을 받는다
- **주기적으로 되비춘다.** 몇 문답마다 "지금까지 정리하면 …" 하고 요약해 보여준다. 사용자가 틀린 해석을 그때 잡아낸다

### 무엇을 물을 것인가

1. **대표 시나리오와 기대값** — 가장 평범한 입력 하나와 그 결과. 도메인 어휘도 여기서 드러난다
2. **결과를 바꾸는 축** — 무엇이 달라지면 답이 달라지는가 (예: 회원 등급·결제 수단·주문 금액). 축이 곧 테스트 리스트의 섹션이 된다
3. **축이 만나는 지점** — 두 규칙이 교차할 때의 우선순위·조합 (여기서 숨은 스펙이 가장 많이 나온다)
4. **경계와 예외** — 0/빈 입력, 상·하한, 정확히 임계값일 때, 잘못된 입력의 처리
5. **스코프** — 이번에 만들지 않을 것. 명시적으로 빼둬야 나중에 "왜 없지?"가 없다
6. **기존 동작과의 관계** (기존 시스템이 있을 때) — 바뀌는 행동이 무엇이고 그대로 둘 것은 무엇인가. 이전 데이터·호출자와의 호환, 마이그레이션이 필요한지

규칙이 **테스트 항목을 쓸 수 있을 만큼** 정해지면 탐구를 멈춘다. 완결이 목표가 아니다 — 큰 도메인이면 첫 섹션 몫만 정하고 나머지는 그 섹션에 진입할 때 다시 묻는다 (아래 *합의 깊이*).

### 탐구의 산출물

- 만들 기능을 한두 문장으로 정의하고, 구현에 필요한 도메인 규칙만 짧게 요약한다
- **용어집을 정리한다** — 여기서 확정한 어휘가 코드·테스트의 이름이 된다 (깊이와 무관하게 초반 확정)
- 대표 시나리오의 기대값을 손으로 계산해 예제 표로 만든다 (오라클 검증 — 기대값이 틀린 테스트는 TDD 전체를 오염시킨다). **점진 깊이에서는 첫 섹션 몫만** 계산하고 나머지는 섹션 진입 시
- **암묵 스펙을 표면화한다**: 테스트 리스트의 모양 자체가 스펙 결정을 내포한다 (예: "결제 대기 중인 주문의 금액 조회" 항목을 두는 것 = "미완결 주문도 조회에 노출한다"는 스펙 채택). 선택지+추천으로 합의한다
- 정의되지 않은 행동을 발견하면 리스트에 넣을지 스코프 밖으로 선언할지 결정한다
- **요구사항 문서·티켓에 오류·모순이 있으면 지적하고 교정 방향을 합의한다** — 문서가 진실인지, 실제 규칙이 진실인지 정한다. 근거 문서가 여러 곳(PRD·이슈·대화)에 흩어져 있으면 **무엇을 기준으로 삼을지**부터 정한다

### 탐구하며 함께 정해지는 두 가지

**작업 유형**과 **합의 깊이**는 별도 관문이 아니다 — 도메인 얘기를 나누다 보면 대개 자연히 드러난다. AI가 결론을 한 줄로 선언하고 1차 승인에 포함시키면 된다. 다만 **결정 자체를 건너뛰지는 않는다** (아래 각 경고 참조).

**작업 유형** — 새로 만드는 기능이면 `동작 변경`이다.

| 유형 | 목적 | 기대하는 첫 신호 | 단계 완료 조건 |
|---|---|---|---|
| **동작 변경** | 없던 행동 추가·기존 행동 변경 | 요구 행동을 표현한 테스트의 Red | 최소 구현으로 합의한 행동이 Green |
| **기존 동작 리팩토링** | 현재 행동을 특성화 테스트로 고정한 뒤 외부 행동 보존하며 내부 구조 변경 | 특성화 테스트의 Green without Red 또는 기존 테스트의 기준 Green | 현재 행동 문서화 + 구조적 완료 조건 + 같은 테스트 Green |

> ⚠️ **기존 코드를 건드리는 작업이면 선언으로 넘기지 말고 반드시 확인받는다.** 실무에서는 이 경우가 더 흔하다. "이 결제 로직 좀 정리해줘"가 리팩토링인지 동작 변경인지는 대화만으로 갈리지 않는데, **첫 신호와 허용되는 코드 변경이 정반대**다. 틀리면 AI가 "정리"하면서 운영 중인 행동을 조용히 바꾼다 — 이 스킬이 막으려는 실패 그 자체다.

- **기존 동작 리팩토링**은 ① 특성화 ② 리팩토링 두 하위 단계로. 특성화가 끝나 기준 테스트 전체 Green을 확인하기 전에는 리팩토링을 시작하지 않는다
- 기존 테스트가 현재 행동을 충분히 보호하면 근거와 실행 결과를 제시하고 승인받아 특성화 추가를 생략할 수 있다
- 한 요청에 두 유형이 섞이면 단계를 분리한다 (예: **기존 동작 리팩토링 → 동작 변경**). 한 시점에는 한 유형만
- 각 단계의 **예상 Red/Green 모양, 허용되는 운영 코드 변경, 완료 조건**을 spec에 기록한다

**합의 깊이** — 규칙 분량·규칙 간 교차·예상 항목 수·오라클 손계산량을 신호로 삼는다 (기계적 임계치가 아니라 근거).

| 깊이 | 대상 | 초반에 확정하는 것 | 진행 중 |
|---|---|---|---|
| **경량** | 규칙 한두 개, 항목 10개 안팎 (입력 검증, 포맷 변환) | 규칙 요약 + 리스트 전량. 오라클은 대표 몇 개 | 그대로 소진 |
| **표준** | 규칙 서너 개, 항목 10~25개 (배송비 정책, 재고 예약) | 용어집·확정 스펙까지 + 리스트 전량 | 필요 시 항목 추가 |
| **점진** | 규칙 다섯 개 이상·교차 많음, 항목 25개+ (요금 정산, 보험료 산출, 수수료 배분) | **뼈대 스펙 + 첫 섹션 항목만**. 나머지 섹션은 제목 + 한 줄 의도만 | **섹션 진입 시 그 섹션의 항목·오라클을 구체화**(합의 커밋) |

> ⚠️ **깊이를 정하지 않으면 AI는 리스트를 전량 작성한다.** 큰 도메인에서 그 정밀도는 재협상 한 번에 통째로 무효가 된다 — 초반 합의의 수명은 규모에 반비례한다. 결론을 한 줄로 선언하고 **spec 파일에 기록한다** (다음 세션이 재발명하지 않도록).

**점진에서 미루는 것**: 뒤쪽 섹션의 개별 항목·손계산 오라클·경계 케이스. **미루지 않는 것**: 도메인 모델의 축(용어집) — 첫 사이클부터 코드의 이름을 규정한다.

## 2. 테스트 리스트

**이 스킬의 결과물은 "무엇을 테스트할지"까지다.** 어떻게 작성할지(테스트 고도, assertion 라이브러리, 명명·픽스처 방침)와 구현 방향, 진행 모드는 사이클 실행 쪽 몫이다 — 여기서 정하지 않는다.

### 이해관계자가 읽는 문서로 쓴다

리스트는 개발자의 메모가 아니라 **기획자·도메인 전문가가 읽고 "맞다/틀리다"를 판정할 수 있는 문서**여야 한다. 그래야 규칙 오해를 코드가 아니라 리스트 단계에서 잡는다.

- **한 문장의 시나리오로 쓴다** — 명사 나열이 아니라 "…하면 …이다". 상황 → 행동 → 기대값이 한 줄에 담긴다
- **주어는 사람이나 도메인 개념**으로 (고객·관리자·구독자·주문). 클래스·메서드·타입 이름은 쓰지 않는다
- **구체적인 값은 반드시 남긴다** — 시나리오라도 입력과 기대값은 숫자로. 이게 오라클이고, 사이클 중 "공짜 통과" 판단과 Red 예측의 근거다
- **왜 이 케이스인지 읽히게** — 경계·조합·예외는 그 의도가 문장에 드러나게 ("만료 시각 정각이면", "쿠폰과 등급 할인이 겹치면")

| | 예시 |
|---|---|
| ❌ 개발자 메모 | 쿠폰 중복 — 2장 → max 적용 |
| ⭕ 시나리오 | 한 주문에 쿠폰을 두 장 넣으면 **할인액이 큰 쪽 하나만 적용된다** — 5,000원권과 10%(8,000원)면 8,000원 할인 |
| ❌ 개발자 메모 | 재고 부족 시 예외 |
| ⭕ 시나리오 | 재고가 3개인데 5개를 주문하면 **주문이 생성되지 않고 거절된다** — 재고는 3개 그대로 |
| ❌ 개발자 메모 | 등급 할인 + 쿠폰 중복 불가 |
| ⭕ 시나리오 | VIP 등급 할인(5%)과 쿠폰을 함께 쓰면 **등급 할인을 먼저 적용한 금액에 쿠폰이 붙는다** — 10만원 → 9.5만원 → 쿠폰 5,000원 → 9만원 |

**내부 구조가 아닌 행동만** 쓴다 (리스트는 행동의 계약이지 설계의 계약이 아니다). 그러면 어떤 테스트 고도를 택하든 항목이 그대로 살아남는다.

품질 점검 4가지:

1. **크기**: 첫 항목이 기능 전체를 요구하면 더 작은 계단으로 분할한다
2. **커버리지**: 특수 규칙마다 ① 단독 ② 조합·연속 ③ 경계 케이스가 각각 있는지. 통합형 테스트에만 의존하면 단독 케이스가 숨어 실패 신호가 뭉개진다
3. **간격**: 인접 항목의 구현 점프가 크면 중간 계단을 추가한다
4. **정렬**: 뼈대(단순 경로) → 특수 규칙 → 조합 → 경계·통합 순

**문서화 테스트 후보를 미리 표시한다**: 앞 항목의 자연스러운 구현이 통과시킬 것으로 예상되는 항목은 표시해둔다. 예측이 맞으면 문서화 테스트로 추가하고, 틀리면 정상 사이클로 — 어느 쪽이든 데이터가 된다.

**점진 깊이라면**: 첫 섹션만 위 형식으로 채우고, 나머지 섹션은 `## 섹션명` + 한 줄 의도만 남긴다. 품질 점검 4가지는 **각 섹션을 구체화할 때** 그 섹션에 적용한다.

## 승인 절차

**단계별로 승인받는다** — 도메인 합의가 확정되기 전에 리스트까지 한 뭉치로 승인받으면 승인의 해상도가 떨어진다:

1. **1차 (계획 모드 승인)**: 도메인 탐구 결과 — 규칙 요약·용어집·오라클 + 작업 유형·합의 깊이 결론. 테스트 리스트는 포함하지 않는다
   - **탐구 문답은 이 승인 앞에서** 이뤄진다. 승인 요청은 문답을 정리한 결과물로 제시한다 — 질문 하나하나를 승인받는 게 아니다
2. **2차**: 확정된 도메인 위에서 테스트 리스트를 별도 제시

## 산출물 — 세 파일과 합의 커밋

승인이 끝나면 파일을 만들고 커밋한다. **대화가 아니라 파일이 단일 진실 공급원이다** (컨텍스트는 휘발된다).

경로와 커밋 메시지는 아래가 기본값이다. **팀 컨벤션(문서 디렉터리 구조, Conventional Commits 등)이 있으면 그것을 따르고**, 무엇을 택했는지 사용자에게 알린다.

- `docs/tdd/<주제>-spec.md` — **코드로도 스킬로도 복원 불가능한 것**: 작업 유형과 단계 완료 조건, **확정한 합의 깊이**, 도메인 규칙·용어집, 확정 스펙과 스코프 밖 선언, 오라클 예제 표. 넣지 않는 것: API·구현 방향(코드가 진실), 테스트 고도·표기 스타일·진행 모드(사이클 실행 쪽 몫)
- `docs/tdd/<주제>-testlist.md` — 테스트 리스트만
- `docs/tdd/<주제>-refactorlist.md` — 리팩토링 리스트. **시작 시 빈 목록**이며 사이클 후처리에서 채워진다 (자리를 미리 만들어 두는 것)

커밋: `합의: <주제> 테스트 리스트와 합의 스펙`

**인계**: 커밋 후 계약이 준비됐음을 알리고 끝낸다. **사이클 실행은 이 스킬의 일이 아니다.**

- `ai-tdd` 스킬이 설치돼 있으면 그것으로 첫 사이클을 시작하도록 안내한다 (별도 플러그인이다)
- 없으면 계약 파일이 곧 진행 지침임을 알리고, 사이클 원칙을 한 문단으로 요약한다: **한 사이클에 모자 하나** — RED&GREEN(실패 테스트 하나 → 최소 구현 → 전체 Green)과 REFACTOR(기준 Green → 행동 보존 구조 변경 → 테스트 무변경 Green)를 섞지 않는다. Red·Green 판정은 실제 테스트 출력으로 증명하고, 사이클마다 리스트 파일을 갱신하며 1커밋을 남긴다

## 재합의 — 정상 절차다

진행 중 도메인 모델의 축이 바뀌는 일은 예외가 아니라 **실무에서 정상적으로 일어난다** (예: "구독 해지는 즉시가 아니라 현재 결제 주기 말에 반영된다"는 정책이 뒤늦게 드러나, 해지를 상태 변경이 아닌 **예약**으로 재정의해야 했던 사례). 이때는 사이클을 멈추고 이 스킬로 돌아온다.

반영 순서 — **문서 → spec → testlist → 코드**:

1. **요구사항 문서**를 고친다 — 저장소 안의 문서면 직접 수정(교정 사유 명시), 외부 문서(PRD·티켓)면 고칠 수 없으므로 **바뀐 내용과 합의 경위를 spec에 남기고** 원 문서 갱신은 사람에게 맡긴다
2. **spec 파일**: 새 확정 스펙(S번호)을 추가하고, 무효가 된 결정에 개정 표시. 용어집 갱신
3. **testlist 파일**: 재정의·분할·스코프 밖 처리된 항목을 사유와 함께 갱신 (완료 항목은 지우지 않고 이력 보존)
4. `합의: <무엇을 왜 바꿨는지>` 커밋 — 여기까지가 재합의
5. 코드 반영은 이 스킬이 아니라 **별도 REFACTOR 사이클**로 (행동 보존 증거 필요)

재합의 후 남은 섹션의 구체화 계획도 다시 본다 — 축이 바뀌면 뒤쪽 항목의 오라클이 통째로 달라질 수 있다.
