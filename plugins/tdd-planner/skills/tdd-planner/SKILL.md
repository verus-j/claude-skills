# TDD 계획 — 계약을 쓰는 시간

사이클이 계약의 이행이라면, 계획 단계는 **계약을 쓰는 시간**이다. 코드 수정이 차단된 계획 모드에서 컨텍스트를 쌓고, 합의 산출물(spec·testlist·refactorlist)을 남긴 뒤 사이클 실행에 인계한다.

**계획 모드에 진입해 시작한다.** 진행 중이던 작업을 **재개**하는 세션은 이 스킬이 아니다 — spec·리스트 파일이 복원 지점이며, 사이클 실행 쪽(`ai-tdd` 스킬이 있으면 그것)으로 바로 간다.

## 0. 규모 판정 — 합의 깊이를 먼저 정한다

**큰 도메인일수록 초반 합의의 수명이 짧다.** 진행 중 도메인 이해가 깊어지면 초반에 정밀하게 정한 오라클·항목이 재협상으로 뒤집힌다. 그래서 합의 깊이를 규모에 비례시킨다.

판정 신호(기계적 임계치가 아니라 근거로 삼는다):

- 도메인 규칙의 분량과 규칙 간 교차(규칙 A가 규칙 B의 입력이 되는가)
- 예상 테스트 항목 수 — 대략 훑어 셀 수 있다
- 미정의 스펙·해석 여지의 많음
- 실데이터·오라클 손계산의 필요량

**AI가 신호를 근거로 깊이를 추천하고, 사람이 확정한다.**

| 깊이 | 대상 | 초반에 확정하는 것 | 진행 중 |
|---|---|---|---|
| **경량** | 규칙 한두 개, 항목 10개 안팎 (볼링·FizzBuzz류) | 스펙 요약 + 테스트 리스트 전체 | 그대로 소진 |
| **표준** | 규칙 서너 개, 항목 10~25개 | 합의 1~5 전체 (아래 절차) | 필요 시 항목 추가 |
| **점진** | 규칙 다섯 개 이상·교차 많음, 항목 25개+ (요금 정산류) | **뼈대 스펙 + 첫 섹션 항목만**. 나머지 섹션은 제목 + 한 줄 의도만 | **섹션 진입 시 그 섹션의 항목·오라클을 구체화**(합의 커밋) |

확정한 깊이는 spec 파일에 한 줄로 기록한다 — 다음 세션이 재발명하지 않도록.

**점진에서 미루는 것**: 뒤쪽 섹션의 개별 항목·손계산 오라클·경계 케이스. **미루지 않는 것**: 작업 유형, 도메인 모델의 축(용어집), 공개 API 골격, 테스트 고도 — 이건 첫 사이클부터 코드를 규정한다.

## 1. 작업 유형 분류

코드나 테스트를 쓰기 전에 현재 작업 단계를 분류하고 승인받는다:

| 유형 | 목적 | 기대하는 첫 신호 | 단계 완료 조건 |
|---|---|---|---|
| **동작 변경** | 없던 행동 추가·기존 행동 변경 | 요구 행동을 표현한 테스트의 Red | 최소 구현으로 합의한 행동이 Green |
| **기존 동작 리팩토링** | 현재 행동을 특성화 테스트로 고정한 뒤 외부 행동 보존하며 내부 구조 변경 | 특성화 테스트의 Green without Red 또는 기존 테스트의 기준 Green | 현재 행동 문서화 + 구조적 완료 조건 + 같은 테스트 Green |

- 사용자 의도·현재 운영 코드의 행동·기존 테스트 유무를 근거로 유형과 추천을 제시한다. AI가 암묵적으로 정하지 않는다
- **기존 동작 리팩토링**은 ① 특성화 ② 리팩토링 두 하위 단계로. 특성화가 끝나 기준 테스트 전체 Green을 확인하기 전에는 리팩토링을 시작하지 않는다
- 기존 테스트가 현재 행동을 충분히 보호하면 근거와 실행 결과를 제시하고 승인받아 특성화 추가를 생략할 수 있다
- 한 요청에 두 유형이 섞이면 단계를 분리한다 (예: **기존 동작 리팩토링 → 동작 변경**). 한 시점에는 한 유형만
- 각 단계마다 **작업 유형·하위 단계, 예상 Red/Green 모양, 허용되는 운영 코드 변경, 단계 완료 조건**을 기록한다

## 2. 기능 정의와 도메인 규칙

- 만들 기능을 한두 문장으로 정의하고, 구현에 필요한 도메인 규칙만 짧게 요약한다
- **용어집을 정리한다** — 여기서 확정한 어휘가 코드·테스트의 이름이 된다 (깊이와 무관하게 초반 확정)
- 대표 시나리오의 기대값을 손으로 계산해 예제 표로 만든다 (오라클 검증 — 기대값이 틀린 테스트는 TDD 전체를 오염시킨다). **점진 깊이에서는 첫 섹션 몫만** 계산하고 나머지는 섹션 진입 시
- **암묵 스펙을 표면화한다**: 테스트 리스트의 모양 자체가 스펙 결정을 내포할 수 있다 (예: "프레임 하나짜리 테스트 허용" = "진행 중 게임의 score() 조회 허용"). 선택지+추천으로 합의한다
- 정의되지 않은 행동을 발견하면 리스트에 넣을지 스코프 밖으로 선언할지 결정한다
- **원본 규칙 문서에 오류·모순이 있으면 지적하고 교정 방향을 합의한다** — 문서가 진실인지, 규칙이 진실인지 정한다

## 3. 공개 API · 테스트 작성 방식 · 구현 방향

- 테스트가 사용할 인터페이스를 먼저 합의한다 (예: `game.roll(pins)` / `game.score()`). 도메인 개념을 API에 노출할지 내부에 둘지도 이때 언급한다
- **테스트를 어떻게 작성할지 합의한다** — 진행 중 즉흥 결정하면 전환 비용이 쌓인다:
  - **테스트 고도**: 최상위 API 시나리오로만 관찰할지(내부 전체가 리팩토링 자유 영역), 도메인 객체별 단위로 관찰할지(실패 국소화 정밀), 혼합할지 — 트레이드오프+추천을 제시하고 사람이 결정한다. **계약 밖으로 둘 내부 구조를 명시한다.** 진행 중 상위 Red의 원인이 애매해지면 하위 테스트 추가를 그때 승인받는 탈출구를 둔다
  - **표기 스타일**: assertion 라이브러리, 테스트 명명 규칙
  - **셋업 방침**: 픽스처·헬퍼의 형태. 처음부터 완벽할 필요는 없고, 보일러플레이트가 반복되면 리팩토링 리스트에 올린다
- **구현 방향을 가볍게 스케치한다**: 유력한 내부 구조 후보를 트레이드오프와 함께 한두 문장씩. 단 스케치는 **약속이 아니라 가설이다** — 테스트가 다른 방향을 강제하면 폐기하고, 스케치를 근거로 선행 구현하지 않는다

## 4. 테스트 리스트

각 항목은 **관찰 가능한 행동 하나 + 대표 입출력 예시**로 쓴다 (예: "스페어 보너스 — 5,5 / 3 → 16"). 예시가 있어야 사이클 중 "공짜 통과" 판단과 Red 예측이 정확해진다. **공개 API로 관찰 가능한 행동만** 다룬다 — 합의 3의 내부 구조 스케치를 검증하는 항목을 넣지 않는다 (리스트는 행동의 계약이지 설계의 계약이 아니다).

품질 점검 4가지:

1. **크기**: 첫 테스트가 전체 시나리오를 요구하면 더 작은 계단으로 분할한다
2. **커버리지**: 특수 규칙마다 ① 단독 ② 조합·연속 ③ 경계 케이스가 각각 있는지. 통합형 테스트에만 의존하면 단독 케이스가 숨어 실패 신호가 뭉개진다
3. **간격**: 인접 항목의 구현 점프가 크면 중간 계단을 추가한다
4. **정렬**: 뼈대(단순 경로) → 특수 규칙 → 조합 → 경계·통합 순

**문서화 테스트 후보를 미리 표시한다**: 앞 항목의 자연스러운 구현이 통과시킬 것으로 예상되는 항목은 표시해둔다. 예측이 맞으면 문서화 테스트로 추가하고, 틀리면 정상 사이클로 — 어느 쪽이든 데이터가 된다.

**점진 깊이라면**: 첫 섹션만 위 형식으로 채우고, 나머지 섹션은 `## 섹션명` + 한 줄 의도만 남긴다. 품질 점검 4가지는 **각 섹션을 구체화할 때** 그 섹션에 적용한다.

## 5. 진행 모드

기본은 사이클 단위 승인 — 사이클이 끝날 때마다 요약을 보고하고 다음 작업 선택을 기다린다. git 사용 여부와 커밋 규칙 적용도 이때 확정한다. **스킬 기본값에서 벗어난 합의만** spec 파일에 기록한다.

## 승인 절차

**단계별로 승인받는다** — 도메인 합의가 확정되기 전에 리스트까지 한 뭉치로 승인받으면 승인의 해상도가 떨어진다:

1. **1차 (계획 모드 승인)**: 규모 판정 + 합의 1(작업 유형) + 2(기능·도메인 규칙) + 3(API·테스트 방식·구현 방향). 테스트 리스트는 포함하지 않는다
2. **2차**: 확정된 2·3 위에서 합의 4(테스트 리스트)를 별도 제시
3. **3차**: 합의 5(진행 모드)

## 산출물 — 세 파일과 합의 커밋

승인이 끝나면 파일을 만들고 커밋한다. **대화가 아니라 파일이 단일 진실 공급원이다** (컨텍스트는 휘발된다).

- `docs/tdd/<주제>-spec.md` — **코드로도 스킬로도 복원 불가능한 것**: 작업 유형과 단계 완료 조건, **확정한 합의 깊이**, 도메인 규칙·용어집, 확정 스펙과 스코프 밖 선언, 오라클 예제 표. 넣지 않는 것: API·구현 방향 스케치(코드가 진실), 테스트 표기 스타일(테스트 코드가 진실), 스킬 기본값 그대로인 진행 모드
- `docs/tdd/<주제>-testlist.md` — 테스트 리스트만
- `docs/tdd/<주제>-refactorlist.md` — 리팩토링 리스트 (시작 시 빈 목록)

커밋: `합의: <주제> 테스트 리스트와 합의 스펙`

**인계**: 커밋 후 계약이 준비됐음을 알리고 끝낸다. **사이클 실행은 이 스킬의 일이 아니다.**

- `ai-tdd` 스킬이 설치돼 있으면 그것으로 첫 사이클을 시작하도록 안내한다 (별도 플러그인이다)
- 없으면 계약 파일이 곧 진행 지침임을 알리고, 사이클 원칙을 한 문단으로 요약한다: **한 사이클에 모자 하나** — RED&GREEN(실패 테스트 하나 → 최소 구현 → 전체 Green)과 REFACTOR(기준 Green → 행동 보존 구조 변경 → 테스트 무변경 Green)를 섞지 않는다. Red·Green 판정은 실제 테스트 출력으로 증명하고, 사이클마다 리스트 파일을 갱신하며 1커밋을 남긴다

## 재합의 — 정상 절차다

진행 중 도메인 모델의 축이 바뀌는 일은 예외가 아니라 **큰 도메인에서 정상적으로 일어난다** (예: "지하철 별도운임 노선은 게이트에서 재태그하므로 별도 탑승이다"라는 사실이 뒤늦게 드러나 탑승 모델 자체가 재정의된 사례). 이때는 사이클을 멈추고 이 스킬로 돌아온다.

반영 순서 — **문서 → spec → testlist → 코드**:

1. **원본 규칙 문서**를 고친다 (버전을 올리고 교정 사유를 남긴다). 문서가 없으면 이 단계 생략
2. **spec 파일**: 새 확정 스펙(S번호)을 추가하고, 무효가 된 결정에 개정 표시. 용어집 갱신
3. **testlist 파일**: 재정의·분할·스코프 밖 처리된 항목을 사유와 함께 갱신 (완료 항목은 지우지 않고 이력 보존)
4. `합의: <무엇을 왜 바꿨는지>` 커밋 — 여기까지가 재합의
5. 코드 반영은 이 스킬이 아니라 **별도 REFACTOR 사이클**로 (행동 보존 증거 필요)

재합의 후 남은 섹션의 구체화 계획도 다시 본다 — 축이 바뀌면 뒤쪽 항목의 오라클이 통째로 달라질 수 있다.
